Function pipelines
Function pipelines are a fundamental concept in functional programming, dating back to the
pipe operator in Unix shells (1970s) and higher-order functions in languages such as Lisp and
ML. The pattern of chaining transformations (map, filter, fold) has been standard in
functional languages since the 1970s. Languages such as Haskell, OCaml, and Scala have made
extensive use of iterator-style pipelines for decades.
idx_b2d2c44f
What Rust brings to this well-established pattern is zero-cost abstraction and ownership
integration. Rust's iterator chains compile to the same efficient machine code as hand-written
loops, sometimes even more efficient due to compiler optimizations. The ownership system
ensures that iterator pipelines respect borrowing rules, preventing data races and use-after-
free bugs at compile time. This makes functional-style pipelines practical for systems
programming where performance and safety are critical.
idx_93ee2ff9
The power of this pattern lies not only in its elegance but also in its ability to outperform
handwritten loops due to lazy evaluation. This challenges the notion that functional-style code
requires performance sacrifices.

invalid ones, grouping by topic, and generating statistics. The imperative approach would use

Generics as type classes: revisiting TypeState
Type classes originated in Haskell as a solution to ad hoc polymorphism, introduced in Philip
Wadler and Stephen Blott's 1989 paper, How to Make Ad-Hoc Polymorphism Less Ad Hoc
(https://dl.acm.org/doi/10.1145/75277.75283). The concept allows defining behavior
that works across multiple types while maintaining type safety through parametric
polymorphism with constraints. This has been a fundamental feature of Haskell's type system
for over three decades.
idx_b3338ec2
Rust's trait system is explicitly inspired by type classes, though adapted for systems
programming. Rust traits provide the same core capability, abstracting over behavior rather
than just data, but integrating with ownership and borrowing rules. Where Haskell type
classes work in a garbage-collected environment, Rust traits must respect lifetime constraints
and ownership transfers. This adaptation makes type-class–style programming practical for
systems code, where manual memory management and zero-cost abstractions are essential.
In this section, we'll enhance the TypeState pattern from Chapter 10, Patterns That Leverage the
Type System, using generics to create more flexible and powerful type-safe state machines, such
as state type markers and a core subscription structure with generic state.339

In Chapter 10, we implemented TypeState with separate impl blocks for each state. This works
but has limitations: adding new states requires modifying multiple places, and we can't write
generic code that works across states with similar capabilities.
Type classes (traits with associated types) solve this by letting us define state transition
capabilities that multiple states can share. A subscription that can be cancelled implements
Cancellable, whether it's Active or Suspended. This enables generic code that works with any
cancellable subscription.
idx_a56939c2
In this design, traits serve as type classes: Activatable, Suspendable, and Cancellable each
define a capability that certain states possess. A Pending subscription implements
Activatable. An Active subscription implements both Suspendable and Cancellable. This is
the type class pattern. We define abstract capabilities as traits and implement them for types
that have those capabilities.

Pattern matching patterns
Pattern matching has been a fundamental feature of functional programming languages since
ML (1973). The concept allows destructuring data structures and binding variables in a single,
exhaustive expression that the compiler verifies for completeness. Languages such as ML,
OCaml, Haskell, Scala, and F# have made pattern matching central to their design, developing
sophisticated techniques over decades of research and practice.
idx_c4c07f81
Rust's pattern-matching implementation draws directly from this functional programming
heritage, particularly ML and its descendants. What Rust adds is integration with the
ownership system and move semantics. Patterns in Rust can move, borrow, or copy valuesChapter 11
346
depending on the context, and the compiler ensures that matched values respect ownership
rules. Exhaustiveness checking interacts with the type system to guarantee all cases are
handled, making pattern matching both safe and zero-cost.
Message routing in Samsa requires checking multiple conditions: message priority, content
type, topic patterns, and payload size. With if/else chains, this logic becomes deeply nested and
hard to verify for completeness. Did we handle all cases? Are any branches unreachable?

Patterns using closures
Closures (also called lambda functions or anonymous functions) are functions that capture
variables from their surrounding scope. Unlike regular functions, a closure can "remember"
values that existed when it was created, carrying that state wherever it goes. This makes them
powerful for callbacks, deferred execution, and creating specialized behavior at runtime.

Closures originated in Lisp in 1958, making them one of the oldest concepts in programming
language design. This long history means closure patterns have been refined over decades.
Functional languages have used closure-based patterns for configuration, callbacks, and
higher-order functions for decades. Languages such as Scheme, Haskell, OCaml, JavaScript,
and many others have developed sophisticated patterns around closures.
What makes Rust's closure implementation unique is how it integrates with the ownership
system. Rust has three closure traits: Fn, FnMut, and FnOnce. These traits explicitly encode how
closures interact with captured values. The compiler automatically infers which trait a closureChapter 11

implements based on how it uses captured variables, ensuring memory safety without garbage
collection. This allows closure-based patterns common in functional and dynamic languages

Closure traits and capture semantics
Understanding Rust's three closure traits helps us write better closure-based code. The Fn trait
is for closures that only borrow values immutably. These closures can be called multiple times.
The FnMut trait is for closures that borrow values mutably. The FnOnce trait is for closures that
consume captured values and can only be called once.

idx_ca9dbb11

Rust automatically infers which trait a closure implements based on how it uses captured
variables. A closure that doesn't modify captures implements Fn. A closure that modifies
captures implements FnMut. A closure that moves captures implements FnOnce. This automatic
inference means we can write natural closure syntax and trust that Rust will enforce correct
usage.
The patterns we'll explore – configurable filters, strategy implementations, and processing
pipelines – demonstrate how closures enable flexible, efficient, and composable code while
maintaining the safety and performance characteristics Rust is known for. Closures in Rust
aren't just convenient syntax for small functions; they're a fundamental tool for building
flexible architectures that remain performant and safe.

The Strategy pattern with closures
The Strategy pattern traditionally uses interfaces or abstract classes to define interchangeable
algorithms. However, defining a new struct and trait implementation for every strategy creates
boilerplate, and strategies can't easily capture runtime state without additional plumbing. In
Rust, closures solve both problems. They provide a more flexible and ergonomic approach. No
separate struct definitions are needed, and closures naturally capture state from their
environment. Instead of defining trait implementations for each strategy, we can use closures
that capture the specific behavior we need.

Processing pipelines with closures
Processing pipelines are another pattern where closures shine. A pipeline is a sequence of
transformations, each of which might fail. Using closures, we can build flexible, composable
pipelines that handle errors gracefully.

Summary
This chapter looked at functional programming patterns that have their roots in languages
such as Lisp, ML, and Haskell. Many years of research and practice have refined these ideas.
What makes these patterns valuable in Rust is not that they're new discoveries, but how Rust
adapts them for systems programming with zero-cost abstractions and compile-time safety
guarantees.
Function pipelines have been fundamental to functional programming since the 1970s. Rust
makes them practical for systems code by compiling iterator chains to efficient machine code
while maintaining ownership guarantees.
Type classes originated in Haskell in 1989 as a solution to ad hoc polymorphism. Rust's trait
system adapts this concept for systems programming, integrating type-class–style abstraction
with lifetime tracking and zero-cost dispatch.
Pattern matching has been central to ML-family languages since 1973. Rust integrates it with
move semantics and the borrow checker, providing exhaustiveness checking and safety
