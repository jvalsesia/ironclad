What Samsa taught us
The Samsa microservice in Chapters 9 through 12 introduced patterns that leverage features
specific to Rust, patterns that would be impossible, impractical, or inefficient in other
languages. These patterns showed what becomes possible when you design from first
principles with Rust's unique features.
idx_91d28644
The NewType pattern wrapped primitive types to add semantic meaning and prevent misuse.
While other languages have similar concepts, Rust's zero-cost abstraction meant these
wrappers added no runtime overhead while providing compile-time safety. We could create
types such as TopicId, ConsumerId, and MessageId that prevented accidentally mixing up
identifiers while compiling to the same efficient representation as raw primitive values.
The parse, don't validate pattern used the type system to maintain invariants throughout the
program. Instead of validating data repeatedly, we validated once at system boundaries and
encoded the validation in types. A TopicId couldn't exist if validation failed, and functions
accepting TopicId knew they were working with valid data without checking.

the consumer lifecycle, as well as in the message processing stages of the system. Operations
that only made sense in certain states became impossible to call in other states. The compiler
ensured that we couldn't poll a consumer that wasn't in the Subscribed state. The poll()
method simply didn't exist for Connected or Paused consumers.
Functional patterns such as iterator chains, Result composition with the ? operator, and

transformation pipelines into efficient loops that eliminated intermediate allocations, and it
also integrated neatly with Result and Option to produce clean, fluent code.
Samsa taught us that Rust enables patterns impossible in other systems languages. The
combination of zero-cost abstractions, a powerful type system, and ownership tracking creates
possibilities unavailable in C or C++ while maintaining the performance characteristics those

The borrow checker as design consultant
Early in our journey with the Bad Calculator, the borrow checker felt like an adversary. Every
attempt to share mutable state triggered errors. Every complex borrowing scenario required
careful thinking about lifetimes. It seemed the compiler was making simple things hard.
idx_a6ebdc43
But as we progressed through the Correct Calculator and Samsa, a different picture emerged.
The borrow checker wasn't making things hard. It was pointing out where our designs had
problems. When we couldn't borrow something mutably because we held an immutable
reference elsewhere, the compiler was telling us that our function had unclear ownership
responsibilities. When lifetime errors appeared, the compiler was revealing that our data flow
wasn't as clear as we thought.
Consider the complex expressions in the Bad Calculator. An early design tried to view and
modify the expression history from multiple places through the same reference. The borrow
checker rejected this, not because it was being difficult, but because the design had a real
problem: we were trying to mutate state we were also reading. The solution wasn't to fight
with lifetimes or wrap everything in RefCell, but to redesign so ownership was clear. The final
design processed one message at a time with clear ownership of expression history, and the
borrow checker approved immediately.
The transformation in thinking comes when you start to trust the borrow checker. When it
complains, instead of looking for workarounds, look for design improvements. More often than
not, the code that satisfies the borrow checker is also clearer, more maintainable, and more
correct than the code you originally tried to write.

The type system as design tool
The type system in Rust goes far beyond catching null pointer errors or type mismatches. Our
three projects showed how types become a primary design tool for encoding domain
knowledge and business rules.
idx_141ab69d
In the Bad Calculator, we used primitive types everywhere: i32 for values, String for
operations, and Boolean flags for state. This approach works in dynamic languages, but in
Rust, it missed the opportunity to use types as documentation and enforcement. Values could
be used in wrong contexts, operations could be invalid, and state invariants existed only in
comments.
The Correct Calculator began using types more intentionally. Enums represented operations
rather than strings. Structs grouped related data. Traits were used to define behavior contracts.
But we still treated types primarily as organization tools rather than design tools.
Samsa took types to their logical conclusion. The TypeState pattern made entire classes of bugs
impossible by encoding state machines as types. Consumer states (Disconnected, Connected,
Subscribed, and Paused) became different types, and transitions became functions that
consumed one type and returned another. You literally couldn't call poll() on an
unsubscribed consumer because that method didn't exist for that type.
The parse, don't validate pattern used newtypes to encode validation in the type system. A
ValidatedTopic could only exist if validation succeeded. Functions accepting ValidatedTopic
didn't need to validate. The type system guaranteed validity. This moved error handling to
system boundaries and eliminated redundant checks throughout the code base.
The lesson is to design with types first. Don't think "I need to store some data; I'll use these
types." Instead, think "What invariants must hold, what states are valid, and what transitions
are legal?" Then, create types that make invalid states unrepresentable. The type system
becomes documentation that the compiler enforces.

Ownership as automatic resource management
Ownership is a complete resource management system, not just memory protection. The
development of our three projects demonstrated how ownership gets rid of whole categories of
resource management issues.
idx_d61a8469
The Bad Calculator demonstrated what happens when you don't trust ownership. Liberal use
of Rc led to unclear ownership semantics and confusion about when resources would actually
be cleaned up.
The Correct Calculator used ownership properly for memory management, but we hadn't yet
explored how ownership applies to other resources, such as file handles, network connections,
or locks. That broader application would come with Samsa. We wrote careful Drop
implementations and tried to ensure that cleanup happened, but it required discipline.
Samsa embraced ownership as comprehensive resource management. Connection pools used
guards that returned connections to the pool when dropped. File handles closed automatically
when they went out of scope. Transaction guards rolled back transactions if not explicitly
committed. The ownership system ensured resources were cleaned up correctly, even in error
paths, without requiring manual try/finally blocks.
The resource acquisition is initialization (RAII) pattern from C++ finds its perfect expression
in Rust. Where C++ RAII requires programmer discipline to avoid use-after-free bugs, Rust's
ownership system enforces correct usage at compile time. You literally cannot use a resource
after it's been dropped because the compiler prevents it.

Ownership as a design philosophy
The Bad Calculator showed what happens when you try to avoid thinking about ownership.
Everything becomes shared and mutable through Rc<RefCell<T>>, leading to unclear

complexity was not in Rust but in avoiding Rust's ownership model.
idx_c90dd5c4
The Correct Calculator started thinking about ownership deliberately. Builder patterns
consumed self to prevent reuse. Factory patterns returned owned values with a clear
ownership transfer. State patterns moved data between states rather than mutating it in place.
These weren't workarounds; they were designs that made ownership relationships explicit.
Samsa was designed with ownership first. The broker owned topics and subscriptions.
Connections owned their state. Messages were owned by exactly one component at a time and
moved through the system with clear ownership transfers. When we needed shared access to

takes ownership consumes the value; the caller can't use it afterward. A function that borrows
immutably allows sharing. A function that borrows mutably requires exclusive access. These
technical details communicate your design intent and allow the compiler to enforce it.
