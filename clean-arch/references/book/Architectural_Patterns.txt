Architectural Patterns
In this chapter, we'll explore architectural patterns by building Samsa, a producer/consumer
(also called pub/sub for "publish/subscribe") microservice. The name is a nod to Gregor
Samsa, the protagonist of Franz Kafka's The Metamorphosis; our Samsa borrows its architecture
from the distributed streaming platform that shares the author's name. We use the term
microservice loosely: our implementation is entirely in-memory, focusing on design patterns
rather than networking or deployment. Chapters 10 through 12 continue building on Samsa,
applying additional Rust patterns to the same codebase.
Architectural patterns operate at a higher level than the design patterns we've seen so far,
shaping how entire systems are organized. In Rust, these patterns are particularly important
because the language's ownership system works best when we design with clear data flows,
contained mutability, well-defined module boundaries, and lightweight data structures from
the start.

Data flows downward
The most important architectural principle in Rust is designing systems where data flows in
clear, predictable directions. Unidirectional, downward data flow minimizes complexity and bugs.
This was true in Java, Python, C++, and every other language. The difference is that those
languages allow you to ignore this principle. Rust doesn't.
idx_78a4609e
When bidirectional communication is needed (such as consumer acknowledgments), the
solution is to create a separate downward channel rather than allowing data to flow back
upstream.

Broker: manages flow direction
The broker is the central component that maintains data flow direction while managing all the
complexity. Here's how we'll build it:

Note
Wait, didn't Chapter 3 say Arc<Mutex< >> is bad?
In Chapter 3, Anti-Pattern: Using Clone and Rc Everywhere, we warned against reflexively
reaching for smart pointers like Arc<Mutex< >> to solve borrow checker issues. So why
are we using it here?
The difference is that pub/sub systems are inherently concurrent. A message broker
exists specifically to allow multiple producers and consumers to share access to topics
simultaneously. This is exactly the use case where Arc<Mutex< >> is appropriate.
Because many producers and consumers can hold references to the same broker, we
need multiple ownership. Because different threads will access the broker concurrently,
we require thread safety. Because multiple threads need to modify the same storage and
offset tracking, we have to share mutable state.
The anti-pattern from Chapter 3 was using smart pointers like Arc<Mutex< >> to fight
the borrow checker, typically in single-threaded code. Here, we're using it because we
genuinely need thread-safe shared ownership.
Don't avoid smart pointers like Arc<Mutex< >> when you actually need them. The
question to ask is: "Do I have a clear reason (like multiple threads that need to share
mutable state) why smart pointers are necessary?" If yes, smart pointers are the right
tool. If not, design with ownership and borrowing first.

The borrow checker enforces good design
When you try to violate unidirectional flow, Rust stops you. Rust's type system prevents us
from creating a web of dependencies that lead to maintenance nightmares. The compiler forces
us to think about ownership and data flow before we can even run our code.
idx_68d07147
idx_06153891
Instead of discovering architectural problems months later during debugging sessions, Rust
catches them immediately. If consumers need to send acknowledgments, we're guided toward
better patterns, like creating a separate downward flow through the broker rather than
reaching back upstream.
This architectural principle was always good practice in every language. Rust simply enforces
it.
Benefits of downward data flow
Designing with downward data flow provides several advantages:
idx_aaf05be2
•Predictable debugging: When something goes wrong, you know data only flows in
one direction, so the source is always upstream
•Easier testing: Each component can be tested in isolation by providing mock inputs
from above
•Clear dependencies: Components only depend on what's above them, never on what's
below
•Natural concurrency: Downward flow maps well to message-passing patterns and
async processing

The second principle is confining mutability to specific, well-defined components. In other
languages, state can be mutated from anywhere. Rust's ownership system forces us to be
explicit about where mutation happens.

Pack lightly
The final principle is designing data structures that minimize borrowing conflicts. Large,
monolithic structs create problems because you can't borrow different parts independently.

This structure creates borrowing conflicts because Rust treats the entire struct as one
borrowing unit. If you tried to write a method like fn publish_and_record(&mut self) that
calls self.messages.insert(...) and self.metrics.insert(...), it would work because
both go through the same &mut self. But you cannot pass &mut self.messages to one
function and &mut self.metrics to another in the same scope, because Rust sees both as
borrowing from the same struct. You can't simultaneously borrow messages and metrics
because they're part of the same struct, even though they're logically independent.
Operations that should be independent (recording metrics and fetching messages) become
impossible or require complex workarounds. The code either becomes overly complicated with
workarounds or suffers from performance bottlenecks.

or writing. RwLock allows multiple simultaneous readers or one exclusive writer, making it a

references have a well-defined lifetime: the compiler must be able to prove that the referenced

example), cloning may be the simplest solution. However, within a single thread and a well-
defined scope, we can use references to avoid copying data entirely. Because we've designed
Samsa with clear, downward data flow, we know exactly how long messages live and who

infer the lifetime from context. In this case, it infers that the view borrows from &self, so the
MessageView cannot outlive the Message it references.
MessageView provides read-only access to message data without cloning. The lifetime
parameter 'a ensures the view cannot outlive the original message, preventing dangling
pointer issues while avoiding allocation costs.
Views eliminate unnecessary memory allocations when components only need to read data.
Consumers can process messages without copying large payloads, improving performance
while maintaining memory safety through Rust's lifetime system.

Summary
In this chapter, we explored four architectural principles that Rust enforces through its
ownership system:
•Data flows downward: Unidirectional flow prevents circular dependencies and makes
systems easier to understand. Our Samsa system flows clearly: Producer → Broker →
Consumer.
•Mutability stays contained: Isolating mutable state makes programs predictable. We
contained all mutation within the broker's controlled interfaces.
•Modules become interfaces: Rust's module system creates architectural boundaries.
We used traits and visibility modifiers to hide implementation details.
•Pack lightly: Thoughtful data structure design eliminates borrowing conflicts. We split
concerns into separate components that can be accessed independently.
