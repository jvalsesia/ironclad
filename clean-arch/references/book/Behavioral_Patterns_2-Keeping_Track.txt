Iterator pattern: efficient collection traversal
The Iterator pattern provides a way to access elements of a collection sequentially without
exposing the underlying representation. Unlike in many other languages where iterators are
implemented as separate design patterns, in Rust they're a core feature of the language, deeply
integrated into the standard library and language syntax. This tight integration makes iterators
both powerful and efficient.

idx_01400bfe
In Rust, the Iterator pattern is formalized through the Iterator trait:

This trait has a single required method, next(), which returns the next element of the
collection, or None if there are no more elements. The trait also provides many default methods,
such as map (which transforms each element), filter (which selects elements matching a
predicate), fold (which accumulates elements into a single value), and collect (which
gathers elements into a collection like Vec or HashMap). Dozens more combinators are
available; see the Iterator documentation in the standard library (https://doc.rust-
lang.org/std/iter/trait.Iterator.html) for the complete list. These build on next() to
create powerful transformations.
What makes Rust's iterators particularly powerful is that they're zero-cost abstractions. They
compile down to efficient machine code with no runtime overhead compared to manual
iteration. Iterators are also lazy: calling filter() or map() does not process any elements
immediately. Instead, it creates a new iterator that will apply the transformation when
elements are eventually consumed by a terminal operation such as collect() or sum(). This
means chaining multiple transformations is cheap; no intermediate collections are created.
When you chain iterator methods like filter().map().collect(), the compiler optimizes
this into a single efficient loop. Rust also provides special syntax for working with iterators: for
loops are syntactic sugar for iterator consumption.

}

As we mentioned earlier, Rust's iterator system is uniquely powerful because it's a zero-cost
abstraction. Iterators are also lazy, meaning they don't process elements until consumed. For
example, a take(5) chain stops after finding five matching items rather than processing the
entire collection.

State pattern: changing behavior based on state
The traditional State pattern allows an object to alter its behavior when its internal state
changes, appearing to change its "class" at runtime. By encapsulating state-specific behaviors
into separate objects and delegating execution to the current state, we eliminate complex
conditional logic and make state transitions explicit and manageable. Rust does not have
classes, but the State pattern lets us evolve the behavior of a type.

Designing the state interface
Before defining the state interface, we need a way for states to communicate their results. A
state's response to input can be a computed value, a mode transition, or an error. We define an
enum to represent these possibilities:

This enum replaces the approach of having states call back into the calculator to change its
state. In Rust, a state can't mutably modify the calculator that owns it. That would require
borrowing the calculator both immutably (through the state field) and mutably at the same
time. Returning the state transition as data avoids this conflict entirely. This approach models
the calculator as a finite state machine, where each mode is a state and
InputResult::ChangeMode represents transitions between states.

Observer pattern: reacting to changes
The Observer pattern establishes a one-to-many dependency between objects so that when
one object changes state, all its dependents are notified and updated automatically. This
pattern is fundamental to implementing event handling systems, reactive programming
models, and components that need to stay synchronized.

The need for reactive components
As our calculator has grown more complex, we've encountered scenarios where multiple
components need to stay in sync. When a variable changes, expressions using that variable
need to be recalculated. When the calculator mode changes, the user interface needs to update
to show appropriate controls. When calculations complete, the history display needs to
refresh. When errors occur, they need to be logged and displayed.

The Observer pattern decouples the subject (the object being observed) from its observers. The
subject maintains a list of observers and notifies them of changes, but doesn't know what they
do with that information. Observers register themselves with subjects they care about and
react when notified.

Throughout our calculator's development, we've built an increasingly complex expression tree

different modes and features, we discovered the need to apply various operations to these
expression trees, including optimization, validation, transformation, and analysis. But how do
we add these operations without continuously modifying our expression structs?

structure they operate on. It allows you to define new operations without changing the
implementations of the elements on which they operate, effectively letting you add new
behaviors to existing structs without modifying them.
The challenge of operating on expression trees
Our calculator's expression tree represents mathematical expressions through a hierarchy of
objects. The expression "3 * (x + 2)" becomes a tree with multiplication at the root, a
number (3) as the left child, and addition as the right child, which has a variable (x) and a
number (2) as its children.
idx_58ea99bd
We want to perform operations like optimizing expressions (replacing "x * 0" with "0"),
validating expressions (checking for division by zero), collecting variable dependencies, and
formatting expressions into different notations. We could add methods for each operation to
every expression struct:

This approach violates the open/closed principle. Every new operation requires modifying the
Expression trait and every type that implements it. The expression types become cluttered
with operations that are secondary to their core purpose of representing mathematical
structure. Testing becomes difficult because each expression type bundles many unrelated
behaviors.

The Visitor pattern separates these concerns. Expression types focus solely on structure,
meaning what kind of expression they represent and what children they have. Operations live
in separate visitor types, each implementing a complete algorithm that traverses the
expression tree.267

Each expression type implements accept by calling the appropriate visitor method. This is
called double dispatch because two method calls are needed to select the right behavior. The
first dispatch occurs on the element: calling accept on a NumberExpression routes to
NumberExpression's accept implementation. The second dispatch is on the visitor: inside
accept, calling visitor.visit_number(self) routes to the specific visitor's handling of
numbers. Neither dispatch alone is sufficient. Without accept, the caller would need to
downcast the expression to determine its type; without the specific visit_* methods, the
visitor couldn't specialize behavior per expression type. The double-dispatch mechanism
ensures the correct visitor method is called based on both the expression type and the visitor
type.

When to use the Visitor pattern
The Visitor pattern fits when you have a stable structure with many operations. Our expression
tree is a good example: the types of expressions (numbers, variables, binary operations,
functions) change rarely, but we frequently add new ways to process them.
idx_6fdbd488
The pattern also suits scenarios where operations need to access concrete types. Each visitor
method receives the specific expression type, enabling type-specific logic without
downcasting. This is the double-dispatch benefit: both the element and visitor types influence
the method called.
Consider the Visitor pattern when you find yourself adding unrelated methods to classes just
because they share a structure, when related operations are scattered across many types, or
when you want to add operations without recompiling the element classes.
The tradeoff is that adding new element types requires updating all visitors. If your hierarchy
changes frequently, visitors become a maintenance burden. For our calculator, expression
types are stable while operations evolve, making Visitor an excellent fit.
Rust's implementation differs from object-oriented languages in a few ways. We can't use
method overloading for the visit methods, so we use explicit names like visit_number and
visit_binary_op. Mutation during traversal requires careful handling due to borrowing rules.
Our optimizer builds a replacement map rather than modifying in place. These constraints
guide us toward cleaner designs.
