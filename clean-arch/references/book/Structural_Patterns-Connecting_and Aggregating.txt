Proxies, decorators, and adapters
These three patterns act as intermediaries that modify how we interact with objects. Each
wraps an existing component to add behavior, control access, or translate interfaces. In
traditional object-oriented languages, all three require substantial boilerplate. Rust's language
features often let us implement them more concisely, and in some cases eliminate the need for
them entirely. In our calculator, we'll use these patterns to add cross-cutting concerns like
logging and caching, and to integrate external mathematical libraries behind a clean interface.
The Proxy pattern in Rust
The Proxy pattern provides a placeholder or surrogate for another object to control access to it.
Traditional uses include lazy initialization, access control, logging, and remote access.
However, Rust's ownership system and standard library often eliminate the need for hand-
written proxies.

Consider lazy initialization, one of the most common proxy use cases. In many languages, you
would write a proxy class that defers construction of an expensive resource (one that involves
significant computation, file or network input/output (I/O), or large memory allocation) until
first use, manually checking whether the inner object has been created on every method call. In
Rust, the standard library provides LazyCell (and its thread-safe counterpart LazyLock) for
exactly this purpose:

their inner types.

The Decorator pattern: extensible expression behavior
The Decorator pattern lets us wrap an object in layers that add new behavior without
modifying the original. As our calculator grows more sophisticated, we need to add cross-
cutting concerns to expressions: logging for debugging, timing for performance analysis,
caching for expensive computations, and range validation for safety. The naive approach

would be to add these capabilities directly to every expression type. Consider what this looks
like:
pub trait Expression {

-> Result<f64, String>;

This bloated trait violates the single responsibility principle. Every expression type, whether it's a
simple NumberExpression or a complex BinaryOperation, must implement methods for
concerns that have nothing to do with expression evaluation. Adding a new concern means
modifying the trait and every implementor. Worse, combining concerns (logging with timing
or caching with validation) requires even more methods, leading to a combinatorial explosion.
With four concerns and the ability to combine them, we'd need fifteen additional methods to
cover every combination.
The Decorator pattern solves this by wrapping expressions in layers that each handle one
concern. Each decorator implements the same Expression trait, delegating the core work to an
inner expression while adding its own behavior before or after. Decorators can be stacked in
any combination without modifying the original expression types. In Rust, this approach
aligns naturally with the trait object system: a decorator wraps a Box<dyn Expression> and
itself implements Expression, making the wrapping invisible to callers.

The caching decorator with interior mutability
The CachingExpression introduces an interesting Rust challenge. Caching requires storing a
result, which involves mutating internal state (storing the computed result so future calls can
return it without re-evaluating), but evaluate takes &self, not &mut self. This is where
interior mutability comes in:

pub struct CachingExpression {
inner: Box<dyn Expression>,

Self {
inner,
last_result: RefCell::new(None),
}
}
pub fn invalidate_cache(&self) {
*self.last_result.borrow_mut() = None;
}
}
The RefCell<Option<f64>> allows us to mutate the cached value through a shared reference.
This is a deliberate trade-off: we move borrow checking from compile time to runtime in
exchange for the ability to cache results without changing the Expression trait's signature.
It is important to understand what runtime borrow checking means in practice: if code calls
borrow_mut() while an immutable borrow (from borrow()) is still active, the program will
panic.
In our CachingExpression, we are careful to ensure that the immutable borrow in the cache
check (the if let Some(result) line) is dropped before we call borrow_mut() to store a new
result. If we accidentally held both borrows simultaneously, we would get a runtime panic
instead of a compile-time error. This is the core risk of RefCell: it trades the compiler's safety
net for flexibility, and the programmer must ensure correct usage.

The Adapter pattern: integrating external libraries
With our decorator implementations complete, we can add logging, timing, caching, and
validation to any expression by wrapping it in layers. But decorators assume that a common
interface already exists. What happens when we need to integrate components that don't
share our Expression interface at all?

another. Our calculator needs trigonometric functions, but different math libraries present
different interfaces. One library might work only in radians, another only in degrees. Some

When to use these patterns
The Proxy, Decorator, and Adapter patterns each serve distinct roles as intermediaries, but
knowing when to reach for each one in Rust requires understanding the alternatives the
language provides.
idx_fc409595
For proxies, check first whether Rust's built-in mechanisms solve your problem. LazyCell and
LazyLock handle lazy initialization. Module visibility (pub, pub(crate)) handles access
control. Smart pointers (Box, Rc, Arc) handle ownership proxying. The Deref trait lets smart
pointers transparently forward method calls. In the rare cases where none of these suffice, a
custom proxy in Rust looks much like a decorator: a struct wrapping the inner type via Box<dyn
Trait>, implementing the same trait, and adding behavior in its method implementations.
For decorators, the pattern works well when you need to add behavior to trait objects
dynamically. If you know at compile time which behaviors you need, consider using generics
with trait bounds instead. A function like the following avoids the overhead of dynamic
dispatch entirely:

The Facade pattern provides a simplified interface to a complex subsystem, hiding the details
of multiple interacting components behind a single, easy-to-use API.

The need for a unified interface
In our calculator, the subsystems include the expression parser, the variable store, scientific
operations, evaluation strategies, and display formatting. Without a facade, every piece of code
that uses the calculator must understand and coordinate all of these pieces individually.

Composites
The Composite pattern lets us treat individual objects and compositions of objects uniformly
through a shared interface. In our calculator, this means a number, a variable, a binary
operation like 2 + 3, and a deeply nested expression like sin(x + 1) * (y - 2) can all be
evaluated, printed, and manipulated through the same Expression trait. The pattern creates a
tree structure where leaf nodes and composite nodes implement the same interface.
idx_c0ae5d85
The challenge of hierarchical expressions
Without the Composite pattern, handling expressions of varying complexity requires case-by-

every combination must be handled explicitly.
The Composite pattern solves this elegantly by defining a tree where every node, whether leaf
or branch, implements the same Expression trait. Think of how you learned operator
precedence in school mathematics: given the expression 2 + 3 * b / 4, you first compute 3 *
b, then divide by 4, then add 2. You are implicitly decomposing the flat expression into a tree of
subexpressions: expr1 = 3 * b, expr2 = expr1 / 4, expr3 = 2 + expr2. The Composite

Flyweight
The Flyweight pattern minimizes memory usage by sharing common data across multiple
objects. In languages where object allocation is expensive and objects carry significant
overhead, flyweight factories that cache and reuse shared state can provide substantial
savings. In Rust, however, the language and standard library provide built-in mechanisms that
serve the same purpose, often more safely and efficiently than a hand-written flyweight
implementation.

In Rust, the Bridge pattern maps naturally to trait objects and composition. The abstraction
holds a Box<dyn Implementation>, just as our CalculatorDisplay holds a Box<dyn
DisplayImplementation>. When both dimensions are known at compile time and you want
maximum performance, consider using generics instead of trait objects: struct
CalculatorDisplay<I: DisplayImplementation> eliminates dynamic dispatch at the cost of
monomorphization.
The Bridge pattern is closely related to the Strategy pattern (which we'll explore in Chapter 7,
Behavioral Patterns 1: Taking Action). Both use composition to delegate behavior to a trait object.
The distinction is in intent: Bridge separates an abstraction's interface from its implementation
across two independent hierarchies, while Strategy provides interchangeable algorithms for a
single behavior. Our evaluation bridge illustrates the overlap: the Evaluator struct holds a
Box<dyn EvaluationStrategy> and delegates evaluation to it, which is structurally identical
to Strategy. What makes it a Bridge as well is that we have two independent trait hierarchies
(EvaluationStrategy for how to evaluate and the Expression tree for what to evaluate) that
vary independently. When you encounter this kind of structural similarity in your own code,
focus on the design intent rather than trying to classify the pattern definitively.

Summary
In this chapter, we explored different structural patterns and saw how Rust's features shape
their implementation.
We began with the Proxy pattern, discovering that Rust's built-in mechanisms (LazyCell,
smart pointers, module visibility) handle most proxy scenarios without custom code, giving us
less boilerplate and stronger compile-time guarantees. The Decorator pattern showed us how
to add cross-cutting concerns like logging, timing, caching, and range validation to expressions
by wrapping them in layers that implement the same Expression trait. Each decorator is
transparent to code that doesn't need its added behavior, and decorators compose freely
through stacking. The Adapter pattern demonstrated how to bridge incompatible interfaces,
allowing our calculator to work with different scientific operation providers through a uniform
ScientificOperations trait.
The Facade pattern gave us CalculatorFacade, a single struct that hides the complexity of
parsers, variable stores, scientific operations, and history tracking behind a simple evaluate
method. We also explored how Rust's module system and pub use re-exports serve as a built-
in facade mechanism at the crate level.
The Composite pattern provided the recursive Expression tree structure that makes our entire
calculator possible. By having leaf nodes and composite nodes implement the same trait, we
can represent and evaluate arbitrarily complex expressions through uniform recursive
traversal.
We briefly examined the Flyweight pattern, finding that Rust's const, static, Arc, and Cow
provide built-in mechanisms for sharing data efficiently.
Finally, the Bridge pattern separated our display abstraction from its implementation,
allowing us to add new output formats without modifying the display logic, and vice versa. A
second bridge for evaluation strategies demonstrated the pattern's versatility.
In the next chapter, we'll shift from structural organization to behavioral patterns, exploring
how the Command, Chain of Responsibility, Strategy, Mediator, and Template Method
patterns can make our calculator interactive and responsive. Where structural patterns defined
how our components connect, behavioral patterns will define how they communicate and
react to user actions.
