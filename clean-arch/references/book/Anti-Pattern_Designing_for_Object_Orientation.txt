In this chapter, we will be discussing an anti-pattern: trying to design for object orientation in
Rust. Anti-patterns are coding solutions that people commonly use in their code but that turn
out to be unhelpful or even counterproductive. These problematic approaches may seem
beneficial at first but ultimately lead to code that is difficult to maintain, inefficient, or prone to
errors. What is unique here is that we will be discussing how a solid design pattern in one
context can be an anti-pattern in a different one.
We will deal with common issues caused by treating Rust as if it were an object-oriented
(OO) language such as Java or C++ and explore common errors from this kind of thinking. We
will learn why OO design patterns cause issues when used in Rust and don't really work as
they should. We will also look at situations where some OO techniques are helpful or even
necessary.
First, we will dig into why Rust may appear to be similar to familiar OO languages, but that
similarity is deceptive. We were introduced to this in the previous chapter, but now we will
look at it in detail, to understand crucial differences.
Next, we will dive into our first trick to try to work with Rust like an OO language: misusing
traits. We will see that while traits resemble abstract classes or Java interfaces, they function
quite differently in many ways, in the context of the language.
The next trick we will cover is trying to use the Deref trait to try to simulate inheritance. We'll
see that this is not a successful strategy and that it can have bad consequences.
We'll also discuss the use, or more correctly misuse, of generics to simulate more traditional

As we saw earlier, Rust can initially appear to support OO programming. This impression isn't
accidental. Rust has many features that bear a surface-level resemblance to OO constructs
from familiar languages. When experienced developers first encounter Rust code, these
similarities create a natural inclination to apply familiar OO patterns.

These surface similarities create a compelling illusion: if Rust has structs, methods, and

OO design approaches? Looking at a screen full of Rust code, it would be natural to see object

However, this is deceptive. If we try to use these features and constructs in the same way that
we are accustomed to using them in a language such as Python or C#, things will seem to work,
even if it is a bit awkward in places, but later our choices will make things very difficult for us.

Structs are not classes
When I first began working with Rust, one of the first things I thought was, "Why are they
calling classes structs?" It seemed clear that these "structs" had methods and fields and
constructors and encapsulation and many, or even all, of the things that you would expect
from a class. The syntax was a bit different, and there did not appear to be any inheritance, but
the differences did not seem significant. It felt like there were "classes" in the language, but, for
some reason, they had been called "structs."
idx_1e6da68f
C was one of the first languages I learned, but Rust structs did not seem much like the simple
structs in C that just collect fields together. They were more like C++ structs, which are almost
identical to C++ classes. So, the decision to use the word struct in Rust seemed aesthetic and
arbitrary.
I understood why the word struct was chosen only after working with Rust for a while: Rust
structs are not classes, and the word struct is much more accurate for describing Rust data
structures.
One of the biggest differences is inheritance. While it has become less popular recently as a
technique, it is the core of polymorphism in OO languages. It is common to structure entire
systems around class hierarchies. Much of the architecture of the system then proceeds from
that class hierarchy. Thinking in terms of class-based polymorphism is very natural in many
popular languages, and the design of the languages themselves supports this.
However, Rust doesn't support this model, but more significantly, it doesn't support this way
of thinking. While it is possible, as we discuss later in this chapter, to use traits for
polymorphism, and while traits do permit some things that look like inheritance, if you beginChapter 2
24
down the road of treating these features as if they are inheritance, you will often find yourself
either entirely blocked by Rust's lack of true inheritance or on a path to more and more
unwieldy designs that are painful to maintain or even understand.
Class hierarchies are hierarchical. They define data and behaviors at the root of the hierarchy,
and then add to them or refine them at each level of the hierarchy. Rust structs don't work that
way. You can't extend or modify their definition by creating children of the struct. A Rust struct
is what it is.
Traits appear to have a kind of inheritance, but they are much more accurately thought of as
contracts. A struct that implements a trait follows that contract, and traits that appear to inherit
from a different trait are more correctly understood to be adding the terms of that trait's
contract to their own.
idx_02c3e536
We run into barriers, or create messy designs, when we try to treat structs as classes by
designing for inheritance, because we can't form real hierarchies. We can draw a diagram and
begin to code thinking in a hierarchical way, but to realize these designs, we need to
laboriously work around the fact that Rust doesn't work that way. This may seem extremely
clear, but it is extremely easy to think hierarchically without even realizing it.
We will see examples of this throughout the book, beginning in this chapter.
Rust has a different take on polymorphism
Polymorphism is built into the essence of classes in most modern OO languages. There is an
inherent expectation that child classes are interchangeable with their parents and siblings. The
language infrastructure is designed to make this effortless and transparent.
In Rust, things are different. After working in Rust for a while, you will become very aware that
Rust types have sizes, because the compiler will remind you of this fact often. Different types
are different things, as far as the compiler is concerned, and if the compiler can't determine
what specific type it is dealing with, it will want to have a word with you. To be able to use two
structs interchangeably, you must take extra specific and explicit steps (which we will discuss)
to make that happen, and we need to follow specific rules and stay within explicit boundaries.
In Rust, it is not possible to substitute types transparently. In some specific circumstances, it is
possible to, for example, declare a function parameter to be of type impl Traitname, and then
call the function with a struct that implements that trait, but that is really syntactic sugar for a
generic type – the actual type is still known at compile time. To work with a truly polymorphic
value, to store a trait in a struct, or call a function with a type unknown at compile time, we
must be explicit and use Box<dyn Traitname>. Using a boxed trait like this is sometimes exactly
what we need. But Rust requires us to affirmatively choose: we must choose to pay the cost of

The borrow checker prevents object patterns
One aspect of OO design is so fundamental, it isn't really even considered to be an OO
paradigm at all. When we design systems using OO patterns, we don't even realize it is there
while we are using it – that is, the free movement of objects.
idx_d29d19a7Chapter 2
26
We can create class hierarchies and designs to leverage polymorphism to make our objects
have proper behavior wherever they are used. But this only becomes truly useful when we can
use our objects everywhere. If we create an object instance of a known type and then call a
method on it a few lines later, that works, and it may look clean and work properly, but we're
not fully using the expressiveness and flexibility of OO patterns. Where it really helps us is
when an object from somewhere else can be doing things that, in this section of the code, we
don't even have to know about.
One of the reasons that OO design has been so successful is that it allows us to create systems
of very high complexity with many, many pieces that are understandable and maintainable.
But to do that, typically, objects travel around the system freely. We don't really think about
that, but it is crucial to the way we think about designing with objects.
In Rust, as we know, we certainly can move data in the form of things such as structs and
enums around the system. But, as we also know, that movement is not exactly free. A very
significant topic of this book, which we will cover in detail, is understanding and thinking
about the flow of data and its central role in designing for Rust. Understanding how your data
flows is crucial for any system design, but Rust has a distinct twist: Rust as a language has
specific rules about how, where, and when data can be shared (which can influence how data
flows through your code). The borrow checker enforces this, and we need to follow its rules.
Because of this, it is vital to think carefully about the design of that flow.
The reason "object-oriented" design is called that is because the design of the objects in the
system takes center stage in the design of the system itself. OO design teaches the habit of
starting from the basis of sound design of the objects in the system. The data flow follows from
that design, and is in service to it. This can work, and data flow can be less of a concern,
because we can count on the languages that we use to allow data to flow (mostly) freely.
This is a crucial element to the way that most modern OO design works. However, this
becomes a recipe for disaster when designing in Rust, because the borrow checker makes us
think much more carefully about the movement and sharing of data.
Pulling it together: types are not objects
Thinking about collections of data in terms of the abstraction of objects is the most
fundamental element of what we think of as OO design. It is the one element that unites all of
the disparate languages, frameworks, models, and patterns that make up object orientation:
they all deal in objects.
idx_81d5f72d
The object is an amazingly useful abstraction. I will not recount its history, but it took the
world by storm (maybe a slow storm at first), for excellent reasons. Being able to model a
collection of data and code in this way has been extraordinarily useful.27

At first glance, Rust seems to be following OO practice. We may not call structs or enums
objects, but they are collections of data, and their impl blocks allow us to group specific code
with specific data structures. They allow (and enforce) encapsulation. Their model of
construction and destruction is a bit unorthodox, but it also fits in this framework. Clearly, this
one aspect of Rust does follow the OO model, right?
Yes, it does, but it also doesn't.
What is at issue is that objects, in an OO sense, come with a set of expectations. It is true that,
by the preceding definition, we can call a struct or an enum in Rust an object, but they are
objects only in this loose sense. We have to be very careful not to allow all of the things that we
have learned to associate with "objects," or even "instances," with these Rust data structures.
Rust works with types that represent data in memory. These types share some superficial (and
some very intentional) characteristics with objects as we know them from OO languages. But it
is tempting to mistake that resemblance for a deeper reality. Rust is not OO. It will be very
helpful to orient yourself away from objects.

Misusing traits
In this section, we will discuss Rust traits and how they can be prone to being misused when
designing in Rust. Traits exist to provide contracts that structs can fulfil, which adds
expressiveness and flexibility to the language. However, we will see why they are not a
substitute for interfaces or abstract classes in the OO sense.
idx_5bad840c
As we discussed in the previous section, Rust traits, while similar to interfaces or pure abstract
classes, do not actually provide or represent the same kind of type hierarchy as classes, and
polymorphism using traits is more circumscribed and less convenient and natural in Rust. It is
tempting to reach for traits as a way to model inheritance, or to try to use them to design
systems that center dynamic polymorphism, but they are not usually the optimal way to
design in Rust, or to create solutions to challenges we will encounter.

Using Deref as a poor substitute for inheritance
We have seen, in the previous section, how traits are not a substitute for inheritance-based
polymorphism. In this section, we will talk about a different strategy to recreate the effects of
class-based inheritance: using the Deref trait.
idx_a2c5aa70
One of the ergonomic features in Rust is automatic dereferencing. Because of the extremely
explicit nature of types in Rust, and because of the many smart pointer types, Rust makes it
simple to use reference types directly, in many circumstances, without having to manually
dereference them.
Rust provides the Deref trait so that you can create your own custom pointer types. The goal is
to allow you to use your new custom pointer as if it were the thing that the custom pointer is
referencing. It makes the reference transparent, making the code clearer and easier to read.
idx_949215a1
But Deref doesn't know or care what it is dereferencing, or even whether it is even
dereferencing anything at all. It knows that it is called on self and that it returns something.
What that something is doesn't matter.
This leads us to our next trick. One thing that we could do to make the code cleaner and
promote reuse is to reduce redundant code in our operators (and everywhere else). In OO
designs, we put code like that in base classes. Rust doesn't have those. What if there were some
trick that we could use to do the same thing?
Deref is a possible answer to this.
