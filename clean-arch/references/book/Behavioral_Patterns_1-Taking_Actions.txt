Command pattern: encapsulating operations
The Command pattern, as traditionally defined, transforms operations into objects, enabling
us to store, pass, and manipulate operations just like any other data. By encapsulating
operations as first-class objects, we gain powerful capabilities, including operation history,
undo/redo functionality, command queuing, and operation logging. This pattern is
fundamental to building interactive applications where users expect to be able to reverse their
actions.
idx_7237e2fe
In Rust, we don't have objects, but the pattern is quite useful regardless. Let's see how we can
realize it in Rust, and how it helps our implementation.
The need for operation management
As our calculator evolves beyond simple expression evaluation, users expect sophisticated
operation management. They want to set variables, clear the calculator state, and most
importantly, undo or redo operations. Managing these diverse operations consistently
becomes challenging, especially when tracking and potentially reversing them.

Without proper encapsulation, undo logic becomes scattered throughout the code base. The
Command pattern offers a solution by encapsulating each operation as an entity that knows
how to execute that operation, undo it if needed, and describe itself for history display.
We'll implement this pattern in three parts: defining a command interface that all operations
implement, creating concrete commands for different calculator operations, and building a
command processor that manages execution and history.
Designing the command interface
In Rust, we define the Command pattern through a trait rather than an abstract class as we
would in an object-oriented language. This trait establishes the contract that each command
must follow:
idx_2da49484
pub trait Command {

String>;
fn undo(&self, calculator: &mut Calculator) -> Result<(), String>;

The execute method takes &mut self because commands need to record state for undo – for
instance, saving the previous value before overwriting it. The undo method only needs &self
since it reads the saved state without modifying the command. The description method
provides a human-readable representation for history display.
Unlike object-oriented implementations where commands might store receiver references,
Rust's ownership model leads us to a different design: commands receive the calculator by
mutable reference rather than owning it. This avoids circular dependencies and lifetime
complexity. The borrow checker ensures that only one command can access the calculator at a
time, preventing the subtle bugs that arise when multiple commands hold references to shared
state.Chapter 7

correctly regardless of the command types involved.

Chain of Responsibility: flexible input processing
The Chain of Responsibility pattern allows us to process requests through a series of handlers,
with each handler deciding either to process the request or to pass it to the next handler in the

The challenge of input processing
Our calculator processes diverse input types: special commands such as /undo or /history
that control calculator state, variable assignments such as x = 5 or result = 2 + 3 that store
values, and mathematical expressions ranging from simple arithmetic to complex nested
calculations. Each input type requires distinct processing logic.
idx_5ae80481
Without a proper pattern, we'd handle all input types with a monolithic conditional block:

if input.starts_with("/") {
// Handle commands...
} else if input.contains("=") {
// Handle variable assignments...
} else {

}
}
This approach quickly becomes unmaintainable as we add features such as function
definitions, mode switches, or macro expansion. Each addition requires modifying the central
processing logic, risking bugs and making the code increasingly complex.
The Chain of Responsibility pattern solves this by creating a pipeline of specialized handlers.
We'll first define a common interface that allows handlers to either process input or decline it.
Then we'll implement concrete handlers for commands, variables, and expressions, and build a
chain that tries each handler in order. This approach makes our input processing both
extensible and maintainable. New input types simply require new handlers added to the chain.

Designing the handler interface
The key design decision is how handlers signal whether they can process a given input. Each
handler needs to either return a result (if it handled the input) or indicate that the next handler
should try. We express this with a return type of Option<Result<Option<f64>, String>>:

&self,

A handler returns Some(Ok(...)) when it successfully processes the input, Some(Err(...))
when it recognizes the input but encounters an error, or None when the input isn't its
responsibility. This three-way signaling (handled, failed, or declined) gives each handler clean
semantics without needing to know about other handlers in the chain.
The Option<Result<...>> nesting may look complex, but it separates two distinct concerns:
Option represents "can I handle this?" while Result represents "did the handling succeed?"
Rust's type system enforces both decisions explicitly, preventing the kind of silent failures that
occur when a handler accidentally swallows input it doesn't understand.
With the handler trait defined, we need a structure to hold and iterate through our handlers:

The InputChain struct stores handlers as trait objects in a Vec, giving us ordered processing
with runtime flexibility. In object-oriented languages, each handler typically stores a reference
to its successor, forming a linked list. In our Rust implementation, a Vec avoids the ownership
complexity of handlers needing to own or reference other handlers. Each handler is
independent; the chain manages the sequence.

Strategy pattern: swappable algorithms
The Strategy pattern allows us to define a family of algorithms, encapsulate each one as a
separate type, and make them interchangeable. This pattern enables the algorithm to vary
independently from the clients that use it, providing a flexible alternative to subclassing for
extending behavior.

The challenge of multiple evaluation approaches
Our calculator needs to handle various evaluation scenarios. Simple expressions require basic
arithmetic, while complex expressions involve variables, functions, and nested operations.
Some users want optimized evaluation that simplifies expressions before computing, while
others need safe evaluation that validates expressions to catch potential errors such as division
by zero.

Note
What exactly is this open/closed principle?
The open/closed principle is one of the SOLID design principles. Bertrand Meyer
originally formulated it in 1988, but it became much more popular when Robert C.
Martin included it in his SOLID principles. What it means is that you should be able to
extend a system's capabilities without modifying its existing code. What makes it
worth paying attention to is that it minimizes the ripple effect of changes: if extending
the system doesn't require changing existing code, you don't need to worry about new
additions destabilizing everything else. It is open to extension, but closed to change.
idx_2f3a4b39
The Strategy pattern solves this by extracting each algorithm into its own type. The calculator
delegates evaluation to whatever strategy is currently active, and strategies can be swapped at
runtime without changing the calculator code.

Mediator pattern: coordinating components
The Mediator pattern addresses a common challenge in complex systems: how to enable
communication between multiple components without creating tight coupling between them.
idx_059b91b3Chapter 7
210
As systems grow, direct communication between components leads to a tangled web of
dependencies that becomes difficult to maintain and extend. The Mediator pattern solves this
by introducing a central coordinator that manages all interactions between components.
In essence, the Mediator pattern defines an object that encapsulates how a set of objects
interact. This promotes loose coupling by keeping objects from referring to each other
explicitly, allowing them to focus on their core responsibilities. We don't have objects in Rust,
but the pattern translates to an effective solution.
The challenge of component coordination
Our calculator has evolved significantly through the previous patterns we've implemented. We
now have several sophisticated components that need to interact: the expression evaluator
(built with our Composite pattern from the previous chapter), the command processor
(managing operation history and undo/redo), a variable storage system, the parser chain (from
our Chain of Responsibility pattern), and multiple evaluation strategies.
idx_bf860d06
Without a coordinating mechanism, these components would need to reference each other
directly. The evaluator would need to know about variable storage to retrieve values. The
command processor would need access to the evaluator to execute operations. Variable
changes would need to notify the display. Each component knowing about multiple others
creates tight coupling. Changing the evaluator's interface would require updating every
component that uses it.
The Mediator pattern breaks these direct dependencies. Each component knows only about
the mediator, and the mediator knows about all components. When the evaluator computes a
result, it notifies the mediator. The mediator then decides which other components need to
know. For example, perhaps the display should show the result, and the history should record
it. The evaluator doesn't know or care about these downstream effects.
We'll implement this pattern in three parts: first, defining the mediator interface and event
types, then showing how components interact with the mediator, and finally implementing
the concrete mediator that orchestrates everything. This is a pattern that works cleanly for one
service, but could also adapt to a multi-service architecture through a communication
interface.

Template Method pattern: structured algorithms
The Template Method pattern provides a way to standardize algorithms while allowing
customization of specific steps. It defines the skeleton of an algorithm in a base type, deferring
some steps to subtypes. This enables code reuse for common algorithm steps while allowing
specific implementations to vary.
idx_a7713982
The challenge of algorithm standardization
Our calculator has grown sophisticated through each pattern we've implemented. We now
have components that process expressions in similar but slightly different ways: standard
arithmetic uses basic operators, scientific mode adds trigonometric functions, and
programmer mode handles different number bases.
idx_7ff47172
Despite these differences, all expression evaluation follows a common sequence:
1.Tokenize the input string into discrete tokens (numbers, operators, functions)
2.Validate the token sequence for basic correctness
3.Parse the tokens into a structured representation (our expression trees from the
previous chapter)
4.Evaluate the structured representation to produce a result
Without standardization, each evaluator would duplicate this flow. The standard evaluator
would implement tokenize–validate–parse–evaluate. The scientific evaluator would implement
its own tokenize–validate–parse–evaluate. Bugs fixed in one might not be fixed in others.
Changes to the flow would require updating every evaluator.
Our Rust implementation of the Template Method pattern extracts this common flow into a
trait, with the fixed structure defined once and customizable steps as methods that
implementations can override. We'll define the trait with the overall algorithm, provide default
implementations for common steps, and require concrete implementations for steps that vary.

When to use the Template Method pattern
The Template Method pattern fits when you have algorithms that share a common structure
but differ in specific steps. Our expression evaluators all tokenize, validate, parse, and evaluate.
The structure is fixed, but tokenization and parsing vary.
idx_387fee31
The pattern also helps when you want to control the algorithm flow while allowing extensions.
The template method defines when validation happens relative to parsing; concrete
implementations can customize validation but can't skip it or reorder it.
Consider this pattern when you find yourself copying algorithm structures between types,
when you need to ensure certain steps always happen in order, or when you want to provide
sensible defaults that most implementations can use unchanged.
The trade-off is rigidity: the template method fixes the algorithm structure. If some evaluator
needs a fundamentally different flow, perhaps parsing and validation interleaved, the pattern
doesn't accommodate that easily. For our calculator, the fixed tokenize-validate-parse-
evaluate flow makes sense across all modes, making Template Method a good fit.
