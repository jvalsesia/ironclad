The allure of ignoring ownership
The ownership structure of Rust may seem like an extra burden to developers when they first
come across it. Rust's stringent guidelines regarding who owns what and when appear
constrictive and annoying to someone from languages where data may be freely exchanged
and altered. Although the fundamental rules themselves are straightforward – each value has
exactly one owner, borrowing allows temporary access without taking ownership, and
mutable borrows are exclusive – it's tempting to look for ways to ignore these rules entirely.
Let's look at how this manifests in our calculator project. We want to add a feature to track
calculation history and allow recalling previous results.
For this feature, our calculator needs to maintain a history of calculations that can be both
viewed and modified by different parts of the program. We want some components to only
view the history, while others need to modify it. In many languages, we might implement this
using interfaces or abstract classes to control access.
In a language such as Java or Python, this would seem relatively simple. Translating this to
Rust, we can create a trait for components that need to access the history and a trait for
components that need to modify the history. We could then implement both traits for

Cloning everything
In this section, we will explore another common anti-pattern: using clone() whenever there is
an error or issue with ownership. Cloning in Rust creates a complete, independent copy of
data. The Clone trait provides a clone() method that duplicates a value, allocating new
memory and copying all contents. While cloning is exactly the tool to use in some situations,
overusing it leads to inefficient code and can mask deeper design issues.

Summary
In this chapter, we explored three common anti-patterns in Rust. We talked about how it is
tempting to avoid thinking about ownership concerns, and we saw the importance of working
with Rust's ownership system rather than against it. Then, we discussed the very common

equally common practice of misusing smart pointers such as Rc and RefCell, and we
