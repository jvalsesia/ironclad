The Result and Option patterns
The Result and Option types come from functional programming languages, particularly ML
and Haskell, where they're known as Either/Maybe and Result/Option, respectively. These
languages established the approach of encoding errors and absence in the type system rather
than using exceptions or null values. OCaml, F#, Scala, and Swift also use similar sum-type
patterns for error handling.
idx_49a294a5
Behind these patterns is the design philosophy that errors and absence are values, not
exceptional control flow. Rather than interrupting program execution with exceptions or
requiring defensive null checks scattered throughout code, Result and Option make failure
modes explicit in function signatures. This forces callers to acknowledge and handle all
possible outcomes at compile time, eliminating entire categories of runtime bugs such as null
pointer exceptions and unhandled errors.
Working with Result and Option effectively means embracing functional programming
patterns that transform and compose these types. Combinators such as map, and_then, and
unwrap_or let you chain operations without explicit matching at every step. Error
transformation with map_err converts between error types as values flow through your
system. Early return composition using the ? operator threads success through pipelines while
short-circuiting on failure. Fallback patterns provide defaults or alternative computations
when operations fail. These patterns combine to create code that handles errors explicitly yet
remains concise and readable.

Patterns using blocks
Expression-oriented programming, where blocks return values, has deep roots in functional
programming. Lisp and its descendants made everything an expression. ML, Scheme, Haskell,
OCaml, Scala, and Ruby all treat blocks as expressions that return values. This isn't a Rust
innovation but a fundamental concept from functional and expression-oriented languages.
idx_1479cb68
idx_fc42be75
What Rust adds is combining expression-oriented programming with the language's
guarantees. Blocks in Rust must respect ownership and borrowing rules. The compiler ensures
that values returned from blocks are properly moved or borrowed. This integration of
expression-oriented programming with compile-time memory safety makes complex
initialization both safe and zero-cost, bringing functional programming elegance to systems
code.
In many languages, statements do things and expressions produce values. In Rust, however,
almost everything is an expression, including blocks, by which we mean code surrounded by {
and }. A { ... } block evaluates to its final expression, which can be assigned to a variable.
This matters because it lets us scope complex initialization logic while keeping the resulting
assignment clean. Variables can be initialized from if/else blocks, match expressions, or
arbitrary computation, all while respecting borrowing rules. We can call this pattern scoped
initialization.

RAII patterns in Rust
RAII was pioneered in C++ by Bjarne Stroustrup in the 1980s as a technique for automatic
resource management through constructor–destructor pairs. The concept ties resource lifetime
to object lifetime, ensuring cleanup happens automatically when objects go out of scope. C++,
D, Ada, and other languages have used RAII patterns for decades.
idx_7db773fc
Rust adapts RAII for memory-safe systems programming through its ownership system. Where
C++ RAII relies on programmer discipline to avoid use-after-free and double-free errors, Rust's
ownership system enforces correct usage at compile time. The Drop trait provides deterministic
destruction, such as C++ destructors, and the Rust borrow checker prevents accessing
resources after they've been dropped. This makes RAII patterns both safe and predictable,
eliminating entire classes of resource management bugs that plague C++ programs.
In Samsa, we manage connections, locks, and transactions. Each resource must be cleaned up
properly: connections need to be returned to pools, locks must be released, and transactions
should either be committed or rolled back. RAII ensures this cleanup happens automatically,
even when errors occur.

Summary
This chapter explored patterns that are, as we noted at the start, the "furniture" of Rust. Where
previous chapters explored techniques that work in the language, these are patterns that grow
out of Rust's very design. Result and Option transform error handling from a burden into an
expressive tool. Block expressions leverage Rust's expression-oriented nature for scoped, clean
initialization. RAII patterns provide automatic cleanup with zero runtime cost. Rust's design
enables remarkably concise yet readable code because of what is built into the language.
These patterns have deep roots in programming language research and practice. Rust
integrates them while adapting these concepts for systems programming and memory safety
guarantees.
We saw this throughout the Samsa microservice: configuration loading that composes
naturally through Result, service initialization that uses blocks to contain complexity, and
connection pools and transaction guards that clean up automatically. These patterns solved
practical problems. More importantly, they felt like the natural way to solve them in Rust.
That's what makes these patterns furniture. You don't think about a chair as "sitting
technology"; you just sit. Similarly, experienced Rust developers don't think, "I'll use the
Result composition pattern here"; they just propagate errors with ? and move on. The patterns
become invisible through familiarity, part of how you think in the language.
As Rust continues to evolve and developers tackle new challenges, new ways of combining
these features will emerge. Remember that patterns are tools to serve your goals, not rules to
constrain your thinking. When you encounter new challenges, draw inspiration from these
patterns, but don't hesitate to develop new approaches when existing patterns don't fit. The
Rust community's strength lies in its willingness to share discoveries and build upon each
other's work.
As you continue writing Rust, you'll find these patterns appearing without conscious effort.
That's the goal. When Result composition, block expressions, and RAII become second nature,
you will move beyond using Rust and begin thinking in it.
